TFCRM PARITY POLICY
1) Authorized results/data source first.
2) Normalized exact/partial search first.
3) Fuzzy matching only when exact/normalized returns zero matches.
4) Human-readable text only may fuzzy-match.
5) Structured values never fuzzy-match:
   - phone
   - email
   - IDs
   - codes
   - campaign/external identifiers
6) Suggestions:
   - start after 2 normalized characters
   - maximum 6
   - use existing authorized data/results; no new unrestricted endpoint
7) Candidate caps after authorization/scoping:
   - Global search: 500
   - normal list/server searches: 1000
8) Voice transcript stays in the exact same typed-search state/pipeline.
9) TCRM Phase 5 learning stays secondary ranking/tie-break only; it must not expand visibility or bypass exact-first matching.

CLIENT-SIDE MIGRATION
For already-authorized in-memory collections, use:
- filterTfcrmParityExactFirst(...)
- buildTfcrmParitySuggestions(...)

Required behavior:
- exact/normalized/contains stage runs across the full authorized collection
- if exact stage has >=1 result, return exact results only
- only if exact stage returns zero, evaluate fuzzy against a bounded candidate set
- candidate set default <=1000; Global <=500
- structured fields are passed only through `structured`, never `text`

SERVER-SIDE MIGRATION
For server-backed search, do NOT keep fuzzyContains in the primary WHERE path if it causes fuzzy results to appear alongside exact results.

Use exact-first two-stage behavior:
- exact query using normalizedContains / normalized exact semantics and existing permission/filter WHERE clauses
- if zero, fuzzy fallback query using existing fuzzyContains for human-readable fields only
- preserve identical auth, ownership, team, tenant, deleted filters, pagination/sort/API shapes
- candidate limit applies after authorized scoping

Use server/utils/searchExactFirstFallback.ts where it fits, or equivalent code preserving the same contract.
